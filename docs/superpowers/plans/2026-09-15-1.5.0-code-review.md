## 评审报告：Xcode 磁盘清理（工作区改动）

**Reviewed:** 2026-09-15T02:23:58Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

Reviewed the uncommitted changes that add an "Xcode 磁盘清理" (disk cleanup) feature:
`XcodeCleanupReporter`/`XcodeCleanupEntry`/`XcodeCleanupSafety` in `Sources/DiskUsage.swift`,
the load/remove orchestration in `XcodeViewModel`, the new `CleanupSectionView` in
`Sources/Views.swift`, and two tests in `Tests/DiskUsageTests.swift`.

The destructive path is the part that matters most, and it is **substantially well guarded**.
`XcodeCleanupReporter.remove(_:)` (`Sources/DiskUsage.swift:167-174`) layers three independent
checks before calling `removeItem`: the target must sit under the resolved home directory,
must match a hardcoded allowlist of known Xcode cache roots (exact match or descendant), and
must not contain a symlinked path component. I found **no path that lets the guard be bypassed** —
notably, `standardizedFileURL` does not resolve symlinks, which is exactly why the separate
`containsSymlinkComponent` walk is needed, and it is present and correct. No critical or
data-loss finding.

The remaining findings are quality and consistency problems: the new user-facing strings were
never added to the String Catalog (so the English build shows Chinese), the shared-entry cache
goes stale for installations other than the one that was rescanned, the same security invariant
is maintained in two hand-written lists that can drift apart, and the "Xcode is running" guard
is enforced only at render time rather than at the moment of deletion.

### WR-02: Force rescan leaves every other installation showing a stale list

**File:** `Sources/ViewModel.swift:276-281` (with `:232-246`, `:266-269`)
**Issue:** The scanned list is global (`XcodeCleanupReporter.entries()` takes no installation), and
`cleanupSharedEntries` caches it, but `completeCleanupLoad` only writes back the entry for the
installation that triggered the scan:

```swift
private func completeCleanupLoad(for id: String, generation: Int, entries: [XcodeCleanupEntry]) {
    guard cleanupScanGeneration[id] == generation else { return }
    cleanupSharedEntries = entries
    cleanupEntriesByID[id] = entries        // ← only this installation is refreshed
    cleanupLoadingIDs.remove(id)
}
```

Reproduce: load installation A (`cleanupEntriesByID[A] = e1`), select B (cache hit at `:235-238` sets
`cleanupEntriesByID[B] = e1`), return to A and press 重新扫描 → A is updated to `e2` but B still holds
`e1`. B keeps showing sizes that no longer exist and entries that were just deleted (or misses newly
appeared ones). `removeCleanupEntry` (`:266-269`) already loops over all keys to avoid exactly this
inconsistency, so the two paths disagree.

**Fix:** refresh every already-loaded installation, since the list is shared:

```swift
private func completeCleanupLoad(for id: String, generation: Int, entries: [XcodeCleanupEntry]) {
    guard cleanupScanGeneration[id] == generation else { return }
    cleanupSharedEntries = entries
    for key in cleanupEntriesByID.keys { cleanupEntriesByID[key] = entries }
    cleanupLoadingIDs.remove(id)
}
```

### WR-03: The cleanup allowlist is duplicated, so the security invariant can drift from the UI

**File:** `Sources/DiskUsage.swift:132-144` vs `:177-191`
**Issue:** The same 13 root paths are written out twice — once as the tuples in `entries()` that
produce what the UI offers, and once as the bare `roots` array in `isKnownCleanupPath` that decides
what `remove` will actually delete. Nothing keeps them in sync. If a directory is added to `entries()`
but not to `roots`, the UI offers it, the user confirms, and the deletion fails for every user with a
misleading "no permission" error (WR-04/IN-03). Conversely, an entry removed from the UI but left in
`roots` stays deletable by any caller that can construct an `XcodeCleanupEntry`.

For a destructive operation the permitted set should have exactly one definition. This is also the
kind of invariant that a future contributor widening the allowlist could weaken without noticing.

**Fix:** define the table once and derive both views from it:

```swift
private struct CleanupRoot {
    let template: String
    let label: String
    let safety: XcodeCleanupSafety
    let note: String
    let expandChildren: Bool
}

private static let roots: [CleanupRoot] = [ /* single source of truth */ ]

static func entries() -> [XcodeCleanupEntry] { /* built from roots */ }

private static func isKnownCleanupPath(_ target: String) -> Bool {
    roots.map(\.template).map { $0.replacingOccurrences(of: "~", with: home) }
        .contains { target == $0 || target.hasPrefix($0 + "/") }
}
```

### WR-04: The "Xcode is running" guard is render-time only, non-reactive, and re-evaluated per row

**File:** `Sources/Views.swift:415,448`; `Sources/ViewModel.swift:228-230,248-274`
**Issue:** Three compounding problems around the only protection against deleting DerivedData out from
under a live build:

1. **Not enforced at the point of action.** The guard exists solely in the view's `.disabled(...)`.
   `removeCleanupEntry` never re-checks, so any caller — or a click that races a state change — can
   delete while Xcode is running. The codebase's own precedent for the analogous hazard is the
   opposite: `activate` re-checks at action time via `runningXcodeDescription` and then shows a modal
   (`Sources/ViewModel.swift:315-329`, `:331-334`).
2. **Stale by construction.** `isAnyXcodeRunning` samples `NSWorkspace.shared.runningApplications`
   on each call, and nothing observes `didLaunchApplication`/`didTerminateApplication` (verified: no
   such observer exists anywhere in `Sources/`). SwiftUI therefore never re-renders when Xcode quits or
   launches, so the orange banner and the disabled buttons describe a state captured at the last
   unrelated re-render. Quitting Xcode leaves every 清理 button disabled until something else
   invalidates the body; launching Xcode leaves them enabled.
3. **Cost scales with row count.** `.disabled(model.isAnyXcodeRunning || ...)` at `:448` is inside the
   `ForEach`, so an N-entry list performs N full application-enumeration passes per body evaluation.

**Fix:** hoist the sample to one evaluation per body and re-check inside the action:

```swift
// Views.swift, once per body:
let xcodeRunning = model.isAnyXcodeRunning
// ...
if xcodeRunning { Label("检测到 Xcode 正在运行。…", systemImage: "pause.circle.fill") }
// ...
.disabled(xcodeRunning || model.isRemovingCleanupEntry(entry))

// ViewModel.swift, defence in depth:
func removeCleanupEntry(_ entry: XcodeCleanupEntry, for installation: XcodeInstallation) {
    guard !isAnyXcodeRunning else {
        isError = true
        statusMessage = String(localized: "检测到 Xcode 正在运行。请退出所有 Xcode 后再清理。")
        return
    }
    // ...existing body
}
```

## Info

### IN-01: Cleanup notes can never be localized because `note` is a plain `String`

**File:** `Sources/DiskUsage.swift:114-123,133-153`; `Sources/Views.swift:438,472`
**Issue:** `XcodeCleanupEntry.note` is declared `String`, is populated with Chinese literals
("编译中间产物，Xcode 会自动重建。", "删除后无法从 Xcode Organizer 恢复归档。", …), and is rendered with
`Text(entry.note)`. Since `note` is `String` rather than `LocalizedStringKey`, SwiftUI picks the
non-localizing `Text(_ content: some StringProtocol)` overload, and the literals are never extracted
into the String Catalog — so unlike every other user-facing string in this feature these cannot be
localized even after WR-01 is fixed. `XcodeCleanupSafety.title` (`:108-109`) does this correctly with
`String(localized:)`.
**Fix:** make the notes localizable at construction, e.g. store
`String(localized: "编译中间产物，Xcode 会自动重建。")` in the table, or set the table's `note` field to
`LocalizedStringKey` and localize when building the entry.

### IN-02: `installation` parameter is unused in `removeCleanupEntry`

**File:** `Sources/ViewModel.swift:248`
**Issue:** `func removeCleanupEntry(_ entry: XcodeCleanupEntry, for installation: XcodeInstallation)`
never references `installation`; the list is global and the mutation loops over every key. Callers
must pass an argument that has no effect, which suggests the operation is installation-scoped when it
is not.
**Fix:** drop the parameter (`removeCleanupEntry(_ entry:)`) or use it to scope the mutation.

### IN-03: A rejected path reports "no permission", which misdescribes the failure

**File:** `Sources/DiskUsage.swift:170-172`; surfaced at `Sources/ViewModel.swift:264-265`
**Issue:** When the guard rejects a target — outside home, not in the allowlist, or containing a
symlink — it throws `CocoaError(.fileWriteNoPermission)`. The UI shows
`String(localized: "清理失败：\(errorMessage)")`, so the user is told they lack permission when the real
reason is that the path is not an approved cleanup target. This is the error path a user hits in the
WR-03 drift scenario, where the message becomes actively misleading.
**Fix:** throw a distinct error with an accurate description, or have `remove` return a
validation failure that the view model maps to a specific message.

### IN-04: The cleanup scan task is not retained, so it cannot be cancelled

**File:** `Sources/ViewModel.swift:242-245`
**Issue:** Every other long-running loader in this class keeps its task so it can be cancelled or
de-duplicated — `detailTasks[installation.id] = Task.detached…` (`:286`), `environmentDoctorTasks`
(`:995`), `runtimeDownloadTask` (`:863`), `signingReportTask` (`:1107`). The cleanup scan is launched
detached and never stored. `[weak self]` prevents a write-back to a dead view model, but the `du`
subprocesses it spawns keep running, and there is no way to cancel a scan the user has navigated away
from. This matters more than usual here because `entries()` shells out to `/usr/bin/du` once per
shared root plus once per child of Archives and iOS DeviceSupport.
**Fix:** store the task in a `cleanupTasks[installation.id]` dictionary (and clear it in
`completeCleanupLoad`), matching the existing loaders.

### IN-05: The generation-mismatch path leaks the loading flag permanently

**File:** `Sources/ViewModel.swift:277-280`
**Issue:** `completeCleanupLoad` returns early when the generation does not match, and
`cleanupLoadingIDs.remove(id)` sits *after* that guard. A dropped completion therefore leaves the
installation in `cleanupLoadingIDs` forever: the row shows "正在扫描目录…" with no way out and
重新扫描 stays disabled (`.disabled(model.isCleanupLoading(...))`, `Views.swift:413`).
The guard at `:233-234` (`!cleanupLoadingIDs.contains(installation.id)`) currently prevents two
overlapping scans for the same id, so I could not construct a reachable trigger — which makes the
generation counter dead defensive code that nonetheless carries a permanent-hang failure mode if it
ever does fire.
**Fix:** remove the loading flag before the guard, or drop the generation counter if the guard at
`:233` is the real serialization point.

### IN-06: `.safe` and `.caution` are cosmetically different but behave identically

**File:** `Sources/Views.swift:427-453,458-473`; `Sources/DiskUsage.swift:101-112`
**Issue:** `XcodeCleanupSafety` is presented as a real distinction — a green check versus an orange
warning, and the section title "清理前确认" ("confirm before cleaning") for `.caution` — but both groups
go through the same `confirmationDialog` and the same `remove` call. A user told that `.safe` entries
are "可直接清理" (directly cleanable) still gets a confirmation prompt, so the classification carries
no behavioral meaning.
**Fix:** either skip the confirmation for `.safe` entries, or make the state a consequence rather than
an input: always confirm, and drop the `.safe`/`.caution` split from the title (keep the note text).

### IN-07: `~` expansion replaces every occurrence and mixes standardized with unstandardized home

**File:** `Sources/DiskUsage.swift:128,147,158,191` vs `:168-170`
**Issue:** `replacingOccurrences(of: "~", with: home)` substitutes *all* `~` characters rather than only
a leading one, and the allowlist/entries build their roots from `home`
(`FileManager.default.homeDirectoryForCurrentUser.path`, `:128`) while the guard compares against
`resolvedHome` (`…standardizedFileURL.path`, `:168`). Both currently resolve to the same string on
macOS, so this is latent rather than broken — but the two checks could disagree if the home path ever
contains a redundant component, in which case the allowlist would stop matching and every cleanup
would fail closed.
**Fix:** expand with a single leading-tilde substitution
(`hasPrefix("~/") ? home + dropFirst() : template`) and compute `home` once, standardized, at `:128`.

### IN-08: The allowlist branch of the removal guard is untested

**File:** `Tests/DiskUsageTests.swift:76-79`
**Issue:** The added test is sound as far as it goes, but
`testCleanupRemovalNeverAcceptsPathsOutsideUserHome` passes `/tmp/not-an-xcode-cache` and relies on the
home-prefix check to reject it. On macOS `/tmp` is itself a symlink to `/private/tmp`, so the test also
passes because of `containsSymlinkComponent` — meaning neither branch it targets is isolated. The most
security-relevant branch, `isKnownCleanupPath` rejecting a path that *is* under home but outside the
allowlist (e.g. `~/Documents`), has no test at all, and no test covers the symlink guard directly.
Test reliability itself is fine; `displaySize == "1 KB"` for 1024 bytes is correct for
`DiskUsageFormatter.humanReadable` (decimal thresholds, 0 decimals for KB).
**Fix:** add cases asserting the allowlist rejects a benign in-home path, and construct a temporary
symlink to assert `containsSymlinkComponent` rejects a path whose ancestor is a link.

**F-1 — `sync_string_catalog.sh` formatting was Xcode-version dependent.** RESOLVED. On this machine

**F-2 — the cleanup scan was sequential.** RESOLVED. `XcodeCleanupReporter.entries()` now measures all

### Design decisions worth recording

**Runtime selection is delegated to simctl, deliberately.** `simctl runtime delete` accepts
`--outdated`, `--unusable` and `--notUsedSinceDays N`. Five iOS 27.0 seeds are installed here
(`24A434`, `24A5370g`, `24A5380g`, `24A5380i`, `24A5355p`) and simctl judges four of them outdated:
its `--dry-run` lists `24A5370g`, `24A5380g`, `24A5380i` and `24A5355p`, keeping `24A434`. That is
not "newest build wins", which is exactly the point — a locally reimplemented rule would have picked a
different survivor. So the app and the CLI show simctl's own `--dry-run` output as the preview and pass
explicit identifiers for single deletions. What the user previews is literally what simctl reports.

An earlier version of this document claimed simctl keeps `24A5380i`; the dry-run above disproves that
and the claim is corrected here.

**`clean` previews by default.** It is the CLI's first destructive command, so removal requires an
explicit `--force`, and the entries Xcode cannot regenerate (archives, device support, package
caches) additionally require `--all`. Those are moved to the Trash; `.safe` caches are deleted
outright, since trashing them would only move the space elsewhere.

**Hidden children are skipped.** The first `clean --all` preview offered `Archive/.DS_Store` and
`iOS DeviceSupport/.DS_Store` as 8 KB cleanup targets, which is Finder metadata rather than an Xcode
artifact; `childEntries` now skips dotfiles.

The test scope cannot use `NSTemporaryDirectory()`: it lives under `/var`, a symlink to
`/private/var`, and a symlinked ancestor is refused by design — so a *successful* removal can never be
driven from there. The scratch directory therefore sits under the real home's `Caches`, and the tests
remove it afterwards.

**Still unverified, and this remains a real gap.** Nothing was actually deleted, and none of the
`simctl` deletion paths ran: all 6 simulator runtimes (~49 GB), the simulator devices and the real
cleanup directories on this machine were left untouched. `simctl runtime delete` (single identifier and
the three bulk selectors) and `simctl delete unavailable` are covered only by parsing,
selector-argument and preview tests. Post-deletion UI behaviour (list refresh, size re-measure,
partial-failure reporting) is likewise unexercised, and the three new UI surfaces — the cleanup section,
runtime reclamation and device deletion — have never been clicked through.

**One process note.** A clean rebuild (`clean build`) was required once: `swift` did not re-emit

— it compares mtimes, not content — but it did surface the problem loudly rather than silently
dropping strings, so it was left alone.
